## خطة النقل الآمنة

### المرحلة 1 — تثبيت مرجع المطابقة
1. حفظ قائمة الصفحات الأصلية، عناصر القائمة، الصلاحيات، أسماء المسارات، ومراجع API لكل صفحة.
2. إنشاء مصفوفة لكل ميزة: موجودة في Android الأصلي؟ موجودة في Flutter؟ endpoint موجود؟ اختبار آلي؟ اختبار حي؟
3. نقل الأصول والهوية والخطوط والثيم وRTL من المصدر، مع الحفاظ على السلوك لا الصورة فقط.

### المرحلة 2 — إكمال تطبيق Flutter
- مطابقة تسجيل الدخول والجلسات، الصفحة الرئيسية والتنقل، الملف الشخصي، الرسائل والمرفقات، الغرف، المقاعد والإشراف، الهدايا، CP والعلاقات، المحفظة والشحن والسحب، الوكالات والمهام، الدراما، الإشعارات، الإعدادات، الصلاحيات والروابط العميقة.
- ربط كل عملية بالـ API الحالي والتحقق من حالات الفشل والصلاحيات والتحديث بعد الحفظ.
- إبقاء تكاملات Android الخاصة التي لا يوجد لها بديل Flutter موثوق على قائمة صريحة قبل الاستبدال.

### المرحلة 3 — نقل الداشبورد إلى Flutter Web
- إضافة تطبيق منفصل داخل `flutter_dashboard/` وعدم إزالة `backend/dashboard/` الحالي.
- نقل شاشة الدخول أولاً مع نفس نموذج المصادقة الحالي، ثم غلاف الإدارة وRTL والثيم والقائمة والصلاحيات.
- نقل الصفحات على مجموعات المجال أعلاه، مع الحفاظ على المسارات وعمليات CRUD والتصدير والرفع والبحث والتصفية والتأكيدات.
- الحفاظ على صلاحيات كل مسار؛ لا يكفي إخفاء زر في الواجهة، ويجب أن يبقى الخادم مصدر التحقق النهائي.
- إبقاء Vue متاحاً كمرجع ورجوع حتى اكتمال مطابقة الصفحات والاختبارات، ثم اتخاذ قرار منفصل بشأن التحويل النهائي.

### المرحلة 4 — بوابات قبول قبل أي استبدال
- Flutter analyze وunit/widget tests وبناء APK.
- بناء Flutter Web واختبارات المسارات والصلاحيات.
- اختبارات تكامل باستخدام حسابات اختبار: مصادقة، رفع صور/ملفات، الرسائل، الغرف، الاقتصاد، الوكالات، CP، الإشعارات وإعدادات الإدارة.
- التحقق من هوية APK `com.Dramizo.Series`، وتوقيع الإصدار، والتثبيت/التحديث على جهاز حقيقي.
- لا دمج ولا نشر تلقائي قبل مراجعة النتائج واعتماد المستخدم.
